# 阶段 11：图片与 ComfyUI worker 缓存恢复（2026-10-04）

## 发现的问题

图片和 ComfyUI 任务的本地记录同时保存在 `CANVAS_TASKS` 内存字典和
`data/canvas_tasks/*.json`。后台 worker 只从内存字典取记录。若提交后同一进程
因为维护清理、异常处理或缓存重建而丢失字典项，worker 仍可能调用上游；完成时
又因 `KeyError` 无法写回，磁盘记录会长时间停在 `queued`/`running`，下一次
查询或重启无法准确解释状态。

## 修改

- `main.py` 新增 `_load_canvas_task_for_worker`。worker 启动时先查内存，缺失时
  在任务记录目录的现有锁规则下读取持久记录；只有 `process_id` 属于当前进程
  且记录仍为 `queued` 才继续执行。重启遗留记录不会被新进程接管，仍由查询
  入口按 `unknown` 边界处理。
- worker 将启动时取得的任务对象保留到完成阶段，因此中途清空内存缓存不会
  丢失成功、失败或即梦排队状态的写回。
- `queued -> running` 的持久写入现在是启动前门禁。运行状态无法保存时，worker
  记录本地失败并停止，不向图片或 ComfyUI 供应商提交请求；保存失败不被伪装成
  已提交。
- 两个入口共用同一规则，未改变任务编号、公开字段、结果白名单和重启未知状态。

## 隔离验证

`tests/test_canvas_task_worker_recovery.py` 共 3 项通过：

1. 清空内存缓存后，图片 worker 从临时目录记录恢复并成功写回；
2. ComfyUI worker 在同样边界下恢复并写回结果；
3. 运行态写入失败时不调用生成函数，并保留可解释的本地失败状态。

同时运行了图片任务生命周期 8 项、跨进程重启边界 3 项、任务并发入口 2 项、
`py_compile`；均通过。测试只使用自制任务和模拟生成函数，没有读取真实 `data/`、
素材、配置或调用外部服务。

## 限制

这项修复只处理同一进程中 worker 与易失缓存的边界。进程硬退出后，图片和 ComfyUI
记录仍按原规则标记为 `unknown`；因为没有可靠的远端编号和查询协议，服务不会自动
重提。跨文件事务、供应商对账、远端取消和真实供应商联调仍属于阶段 11 后续范围。
