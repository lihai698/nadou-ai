# 模块化第五轮 保存排队状态

后续更新：第六轮已将待执行保存计时器迁入 CanvasSaveScheduler，修复普通画布过期句柄导致重复保存的问题；Session 本身继续只管理运行、排队与等待承诺。

2026-10-17。在前四轮基础上，把两种画布的保存运行状态集中到独立模块，接回草稿保留判断。未提交、推送或发布，没有数据格式变化。

## 职责

`CanvasSaveSession.create` 为每个编辑器创建独立对象，拥有 isSaving、queued 和 inFlight，通过 begin、finish、queue、clearQueue 修改。只读 getter 防止其他代码随意覆盖这三个值。

模块没有 DOM、网络、定时器、节点或存储依赖，不需要注册或销毁事件监听器。HTTP 仍由 CanvasSaveTransport 管理；草稿持久化、跨页合并仍由 CanvasSaveRecovery 管理。

两编辑器的清空保护、远端同步、返回列表、保存等待、失败收尾、后续保存和草稿清除判断均迁移到同一实例。旧全局标记 savingCanvasNow/saveCanvasAgain、canvasSyncInFlight/canvasSaveQueued 和 saveCanvas.inFlight 已全局搜索确认清理，无旁路状态或兼容别名。

## 保留行为

- 普通画布开始保存清除旧排队标记；智能画布开始保存保持原标记。这一差异由 create 的单一选项明确表达。
- 完成保存先释放运行状态、清除当前承诺，再唤醒等待者；等待中的调用仍由编辑器检查画布身份，重新取最新快照。
- 保存期间的新编辑标为待保存；成功回包不清除这些尚未保存的草稿。后续快照成功后才清除。
- 智能 409 仍先清除旧排队标记，再等待 JSON/GET；等待期间发生的新编辑仍可重新排队。
- 防抖 500/450ms、后续保存 0/300ms、错误提示、快照、节点合并、任务编号、撤销历史及画布切换逻辑不变。
- 重复 begin 会拒绝内部错误调用，保留当前等待承诺；正常宿主继续使用原忙碌判断。finish 在空闲时可安全重复调用。

草稿宿主未另建一套抽象；本轮只迁移其依赖的排队状态判断，原快照构造与恢复操作留在编辑器。

## 可控延迟界面验收

初始固定 3 秒延迟不能可靠覆盖操作时机，因此没有把它当作并发验收成功。改用仅存在于隔离服务的请求等待标记，明确控制以下顺序：

1. 浏览器编辑第一份文本，服务器记录 PUT 已开始但尚未结束。
2. 在请求仍等待时，通过真实输入框改成最新文本。
3. 再次确认该请求未结束，移除测试等待标记。
4. 原保存返回后，待保存的新快照继续保存；返回列表并重新打开。

普通和智能画布分别完成上述过程，最新中文全文保留。另核对服务器事件记录和磁盘 JSON。测试等待机制只在 `.git/modularization/preview_gate.py` 使用，不进入发布文件或正常运行代码。
