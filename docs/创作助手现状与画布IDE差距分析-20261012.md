# 创作助手现状与画布 IDE 差距分析

日期：2026-10-12。依据当前工作区源码、现有验收记录和3034隔离页面。此次不修改产品代码、不安装框架、不调用真实模型，不把源码存在当作真实服务效果通过。

## 结论

目前是具有画布工具调用能力的早期 Agent，有继续建设的基础；尚未达到用户要求的“通过可安装 Skills 编排、执行并调试创作流程的画布 IDE”。主要差距是可执行工作流、动态 Skill 系统和简洁明确的交互，而不是继续增加工具数量或保护条目。

此前将已填内容的故事节点图称为“完整创作工作流”不准确：助手模型可以在聊天回合里分析并填写内容，但画布图没有对应的阶段性文本模型执行节点。两种画布同步创建成功，只证明类型、内容、连线和保存，不证明正文修改后下游会通过模型重算。

## 参考项目与实际执行器

此前设计参考了Nomi、Pi与DeepSeek Harness。但现有助手主循环仍是本项目Python实现，没有把DeepSeek Harness或Nomi运行时作为现行执行器接入。依据：backend/canvas_assistant_agent.py及docs/创作助手引入方案-20261008.md:797。使用DeepSeek文本模型，不等于安装DeepSeek Harness。此结论来自本地源码与项目记录，不是对参考项目最新版本的外网比较。

## 为什么保护很多但仍然不好用

保护主要解决：重复计费、跨画布写错、覆写用户素材、旧结果误回填、执行失败却声称完成、升级后旧知识失效。它们无法判断某条创作链是否遗漏了LLM分析步骤，或作品是否符合用户期待。

应保留：用户模型选择、原任务编号和去重、原子保存、画布归属、忙碌状态、停止续行及失败回执。不要通过删除这些保护解决可执行流程缺失。

建议调整：

- 当前知识检查在写入前检查整个快照的来源变化。backend/canvas_assistant.py:753、backend/canvas_assistant_knowledge.py:124。共享大文件一处变更可使多个能力过期，建议以后依据本次动作依赖的能力检查；相关规则变化仍应阻止旧规则写入。
- 通用节点操作直接写入，原生动作包括不收费编辑也经方案确认；持久计划另设服务任务额度。依据backend/canvas_assistant.py:752、backend/canvas_assistant_native.py:734、static/js/canvas-assistant.js:98。安全模式并非统一，增加了用户理解成本。应明确“免费可恢复编辑直接执行”“收费运行按一次任务范围确认”“破坏性动作单独确认”。
- 不代选模型是合理要求，但用户已经明确选择的模型应该能通过显式绑定传给新节点。当前原生LLM运行要求用户在每个原节点选择模型，是搭建可执行链必须补齐的接点；不是让助手猜模型。
- 模型仍使用文本JSON决策协议，并兼容DSML。backend/canvas_assistant_agent.py:22、backend/canvas_assistant_tools.py:193。现有协议可用，但复杂批次更容易出现格式/参数纠错；应先衡量实际失败，再决定增加原生tool calling适配，不能直接宣布必须更换整个框架。

## 界面占用的实际问题

源码默认面板300×360像素（static/css/canvas-assistant.css:1）。本次3034页面实测：聊天区约109px，输入与上下文/工具区约162px，画布标题行30px，执行详情折叠行35px；这是该页面当前尺寸，不代表所有用户状态。

执行详情本身已默认折叠，不应误报为所有日志自动展开。问题是仍有多层信息占用：showStatus同步写入状态区及进度标题（static/js/canvas-assistant.js:90），历史回放再显示回复、方案及状态（:451）；持久计划的进度、额度和控制按钮被放在详情折叠区外（:96-120）。多步骤和多方案会继续占据聊天空间。

建议默认只留：对话正文、当前一步简短状态、确实需要用户处理的确认卡。工具日志、回执、计划和预算放入统一折叠详情；完成方案收成一行，可展开查阅。默认扩大阅读空间，输入框随内容增长；不更换本项目配色与组件体系。

## 验收记录应该怎样解读

当前正式清单实际413条，operation为375 pending、33 partial、5 passed；5条passed均属于普通音频的特定合同，不是五条完整创作链。supplierCheck为83 pending、330 not_applicable。这是文档记录，不是此次重新执行的全部功能测试。

此前966个Python/500个JavaScript回归通过证明许多保存、保护和特定行为未被破坏，但没有证明“故事→分析→分镜→图片→视频”全链可执行。不能用测试总数作为用户创作目标的完成率，也不能把pending全部称为已知程序故障。

## 建议实施顺序

1. 收敛目标：画布Agent负责规划、调用工具、检查和恢复；画布节点负责承载真实处理步骤。区分“输出内容结果图”和“可再次执行的工作流”，本项目优先完成后者。
2. 先打通普通和智能的最小链：正文→已绑定用户文本模型的分析步骤→结构化分镜表。验收原文变化后的重跑、错误定位、保存重开及无重复调用，再增加资产与逐镜提示词/媒体步骤。
3. 把正确选节点、接模型、接输入输出、校验执行结果的规则写成内置工作流Skill，并由程序验证。技能不能创造尚未接入的工具。
4. 精简助手状态与确认呈现，保留可展开的真实记录。最小可执行链和精简界面完成前，暂停扩大复杂引擎/拓扑和展示型能力。
5. 依据已有安装设计实现动态Skill目录、来源记录、安装/启停、显式调用与自动匹配。先支持现有画布工具可执行的文档型Skill；依赖终端、脚本或MCP的包要明确兼容范围。
6. 验收以用户任务为单位：从文本生成分镜、改一镜后局部重跑、参考图海报、失败恢复且不重复扣费。每项都检查真实输入、模型调用、输出和重开，而不只看节点数量或接口返回。

本次仅新增分析文档，没有修改、删除或发布产品代码，没有进行真实模型请求。实际供应商稳定性、开放目录全部动作和完整创作质量仍需后续逐任务验证。
