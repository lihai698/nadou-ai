# 阶段 11 视频任务稳定编号实施（2026-10-04）

本次只处理画布视频任务的本地受理边界，没有调用真实供应商，也没有实现“取消远端任务”的假接口。

## 已完成

- 新增 `POST /api/canvas-video-tasks` 和 `GET /api/canvas-video-tasks/{task_id}`。
- 两种画布在发起视频请求前生成并保存 `canvas_video_...` 本地编号；服务端先用原子 JSON 写入最小任务记录，再启动现有视频适配器。
- 相同编号的重复 POST 只返回已有记录，不会重新调用视频供应商。记录只保存供应商编号、模型、状态、时间和本地/上游任务编号，不保存提示词、参考素材、API Key 或完整上游响应。
- 服务重启后，旧进程留下的 `queued/running` 记录会变为 `unknown`，明确提示远端状态未知；页面刷新只查询原编号，不自动再次提交。
- 本地任务记录写入失败、记录损坏或后台任务不能启动时，接口拒绝启动远端请求。
- 明确的 4xx 拒绝记为 `failed`；408、5xx、网络中断和其它未确认结果记为 `unknown`，不虚称远端已取消。

## 验证

- `tests/test_canvas_video_lifecycle.py`：5 项通过，覆盖重复 POST、重启未知、写入失败、上游超时/明确拒绝、损坏记录。
- `node --check static/js/canvas.js`、`node --check static/js/smart-canvas.js` 通过。
- 原有 `tests/smart_canvas_video_unknown.test.cjs` 7 项通过，旧的提交前保存和重复提交警告保持兼容。

## 边界

当前服务重启后对没有远端编号的记录仍只能可靠地说明“远端状态未知”。本轮已为 RunningHub 和已有 GET 长轮询适配器增加 `POST /api/canvas-video-tasks/{task_id}/refresh` 单次查询，并由两种画布的恢复卡片提供“刷新远端结果”；该接口只使用已保存编号，不重新提交。即梦 CLI 视频仍需单独拆出受理回调和查询协议；没有统一的真实远端取消能力，因此界面不会把停止等待写成已取消。详见[视频任务远端刷新与两画布入口](阶段11视频任务远端刷新与画布入口-20261004.md)。
