## 恢复和异常案例

1. 原任务受理后刷新：保存并重新读取同 taskId，提交计数不增加，已保存作品不丢失。
2. 两标签重复确认：只一方取得执行权，供应商只受理批准次数；模型不得自行再提交。
3. 已发送请求但未得到编号：标 submission_unknown，暂停并核对原状态，不自动重试。不得为演练故意造成收费重复或破坏真实任务。
4. 模型无视觉/读不到音频/结果文件不可读：检查状态为无法判断，保存具体范围，不能标作品合格。
5. 作品不满足要求：列证据和位置，提出修正方案；重新生成另行确认，并从累计额度扣除。预算用完保存进度，不自动扩额。
6. 缺失依赖/模型不支持参数/网络错误：真实错误可见，保留输入和已完成操作；不切换用户模型，不关闭门禁。

## 每项证据与通过条件

证据放独立 `output/assistant-real-model-verification/<runId>/`，不提交用户数据、图片、密钥或收费任务记录。每份记录包含：代码/知识版本、caseId/featureId、canvas/session/turn/step/action 编号、用户目标与保留要求、用户选定模型名称、配置能力摘要、批准范围、调用次数/可核对费用、脱敏请求参数、真实 taskId、实际保存回执、原始作品引用/摘要、硬条件结果、语义证据、截图、刷新/恢复证据、已知限制、用户验收状态。

- 模型理解：输出与原生展开/参数/目录一致；未开放能力明确告知。
- 执行：批准范围内实际成功，编号和作品归属可追溯，不重复收费提交。
- 硬条件：原文件可读取、数量/比例/尺寸/时长/声音及必要节点连接符合要求。
- 语义：按用户要求提供具体证据，结论为 passed / needs_revision / inconclusive；任务成功、模型高分或“看起来很好”不独自作为通过条件。
- 界面：普通/智能分别实际操作正常/等待/错误/停止/恢复、中文、图片比例、桌面与390px；原生 UI 保持。
