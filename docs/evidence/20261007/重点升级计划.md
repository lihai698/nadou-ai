# 重点升级计划（2026-10-07）

## 目标与取舍

把项目逐步做成可长期使用的个人自媒体创作工具。优先保证画布、素材和生成任务可靠，修改一个供应商或任务流程时能明确影响范围、发现回归并恢复。文件行数只是定位线索，不作为拆分目标；没有真实问题或明确扩展需求，不继续抽取零散函数。

已确认：`main.py` 约 2.2 万行，视频提交、查询和刷新以及图片生成等流程集中；现有本地模拟回归和完整安装包隔离启动通过。尚未确认：真实 ComfyUI、Agnes 视频协议、macOS、长期压力和真实用户目录跨版本升级。此前模拟测试不能替代这些实际环境验收。

## 对大流程集中度的判断

这属于中长期的高风险维护问题，暂时不是必须停机修复的运行故障。风险主要来自三个方面：

- 修改供应商请求时，容易同时碰到任务状态、页面返回和文件保存，影响范围难以凭函数名判断。
- 一个流程中的异常处理和兼容分支过多，新增模型时容易误用已有协议或错误状态。
- 测试需要围绕整条链路运行，局部改动的回归成本会持续上升。

处理原则是“按业务边界拆，不按行数拆”。在没有真实缺口前，不把 `main.py` 拆成大量小工具，也不引入新的框架或任务系统。每个拆分必须同时满足：真实入口已经找到、输入输出契约已经固定、专项回归已经存在、新模块不反向依赖 `main.py`、旧实现已被新入口完全替代。

本轮的长期维护目标不是让文件看起来更短，而是让以后修改一个供应商或一种任务状态时，可以明确只影响一个适配边界，并且能用一组链路测试证明普通画布、智能画布和历史数据没有回归。

## 执行顺序

### 1. 视频任务完整链路（当前第一项，P0）

先画出普通画布和智能画布实际使用的提交、远端受理编号落盘、GET/刷新、结果保存与重开路径，核对同步 `/api/canvas-video` 与后台视频任务入口的关系。用独立目录和本机模拟回包完成一次完整操作，覆盖成功、明确失败、受理后断线、服务重启、原编号重复查询、部分结果及记录写入失败。检查只有一次上游提交；状态未知时保留编号和用户可见提示，不自动再次计费。发现缺口先做最小修复，再回归两种画布。

验收：记录与页面状态一致，失败不显示成功，重启后可查的继续按原编号查询，无法确认的保持 `unknown`；旧视频任务记录和现有接口仍可读取。交付一份调用关系及数据归属说明、故障复现/修复证据。若没有可复现的缺口，仅固定行为和证据，不为了缩短函数而改写 486 行入口。

视频链路通过后，再做一次职责边界评估。只有当供应商分支继续增加、状态规则出现重复或修改已经需要同时改动多个页面时，才把“视频供应商适配”和“视频任务记录/查询协调”分别移到后端模块；任务记录格式和 HTTP 路径保持兼容。

### 2. ComfyUI 生成与恢复链路（P1）

当前状态：本地模拟链路第一轮已完成并修复成功结果写盘异常边界；任务 worker 生命周期已移到 `backend/comfy_task_service.py`，`main.py` 只保留兼容包装和路由；真实 ComfyUI 实机验收仍待可用服务。

在视频链路稳定后，用自制工作流和模拟 ComfyUI 覆盖普通画布、智能画布的提交、任务编号保存、刷新续查、输出回填、失败与重启。重点检查工作流参数和结果素材不会在页面刷新或保存失败后丢失。真实 ComfyUI 可用时再做一次独立验收；没有环境时明确保留未验结论。

验收：同一任务只提交一次；两种画布保存、重开和错误提示正确；旧画布和工作流格式继续兼容。只有发现 `generate` 的真实职责边界阻碍修改时，才按工作流解析、执行和结果保存的完整职责逐步拆分。

如果继续拆分，先把“工作流输入整理/校验”“ComfyUI 请求与轮询”“结果保存与记录”作为三个可验证边界，入口层只保留组装和 HTTP 错误转换。当前只完成任务 worker 生命周期边界；`generate` 的工作流构造和供应商/实例选择仍留在 `main.py`，等真实需求或扩展受阻时再处理。每次只移动一个边界，移动后删除原重复实现并重新跑同一组测试。

### 3. 图片生成与其他供应商（P2）

当前已先完成低风险的供应商分发边界：`backend/image_generation_dispatch.py` 固定分支优先级，`main.py::generate_ai_image` 保留兼容入口和原供应商实现。专项证据见 `图片生成分发规则拆分.md`。真实供应商请求、远端任务和结果保存暂未移动。

图片任务还发现并修复了“生成成功但最终记录写盘失败”时的非法状态转换；本进程保留结果，重启后保守显示 `unknown`。证据见 `图片结果写盘失败状态修复.md`。

图片生成和供应商连接出现具体故障或新接入需求时，先固定 `generate_ai_image` 的真实调用、输入输出和受理编号，再修改对应供应商分支。素材或画布功能同理：优先解决数据丢失、重复提交、错误成功提示、升级不兼容等实际风险。每次只处理一条完整业务链路，保留原接口与旧数据格式；新实现接入并验证后删除完全替代的旧实现。

`generate_ai_image` 只有在真实修改已被供应商分支、任务状态和结果保存三类职责互相阻塞时才拆分。优先提取“供应商适配器选择”和“远端状态解析”这两个完整边界，保留现有调用方和错误语义。

### 4. 稳定版本交付与维护门禁（每个 P 阶段结束）

每次完成有用户价值的代码变更，运行对应专项测试和两画布受影响流程；发布候选才运行完整核心检查、清单哈希、隔离启动与升级恢复。保留上一稳定目录及独立数据备份。版本、更新说明和安装包必须来自同一份已验证源码；不因文档改动或函数搬家反复生成安装包。真实供应商、收费请求和正式发布另按已确认的环境与授权执行。

每个阶段结束必须形成一份短证据：改动入口、影响范围、状态流转、专项测试结果、未验证环境和回退方式。没有这份证据，阶段不算完成，也不继续扩大拆分范围。

## 本轮明确不做的事情

- 不把 `main.py` 全部重写成新架构。
- 不为了降低行数继续零散抽取格式化、字典拼接和单次判断函数。
- 不引入数据库、消息队列、插件框架或新的供应商协议来“预留未来”。
- 不猜测真实视频供应商字段，不用模拟回包宣称真实供应商通过。
- 不在视频和 ComfyUI 链路没有通过前，继续扩展图片供应商或画布外围功能。

## 每项工作的停止条件

- 无法确认是否重复提交、数据是否保存或状态是否真实时，停止扩大改动，先复现并补证据。
- 相关回归失败时先修复或恢复，不把该版本当稳定版本。
- 真实协议或设备缺失时，不猜字段、不宣称实测通过；继续完成本机可验证部分。

此计划替代此前“继续审计下一个小型供应商适配入口”的优先级，不取消已有阶段路线；阶段 8、9、11 等总阶段仍按原验收条件判断，不因局部拆分勾选完成。
