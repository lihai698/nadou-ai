# 画布存储模块迁移验收

2026-10-18。按用户要求回到模块化主线，完成第一个完整职责域：画布文档存储与锁内更新。此前十三轮修改完整保留，本轮未修改前端逻辑、外部HTTP接口或数据格式，未提交上传。

## 迁出结果

新模块 `backend/canvas_store.py`，256行，拥有17个业务方法：path、validate、write、save、for_project、create、load、load_any、cleanup_trash、records、meta、update_meta、touch、update_content、delete、restore、purge。

`main.py` 从本轮开始时23,484行减少到23,318行，净减少166行。此数值不等于整个主程序完成模块化：媒体、任务、供应商等仍按总清单继续迁移。

| 位置 | 拥有的职责 | 允许依赖 |
| --- | --- | --- |
| CanvasStore | 画布路径与格式、文档读写、新建、目录枚举/回收站、元数据/内容更新、项目迁移前校验 | atomic_json、data_formats、canvas_records；注入目录、共享锁、时钟、ID和writer |
| main._canvas_store | 每次调用提供当前配置与同一把CANVAS_LOCK，领域错误转换为原HTTP状态和detail | CanvasStore；没有存储算法副本 |
| main路由 | 请求校验、响应包裹、画布更新广播 | 存储方法；保持原路由与响应字段 |
| project_service | 项目删除时逐画布迁移与项目索引协调 | 既有适配函数现在委托CanvasStore，仍共用同一锁 |

新模块不导入 main/FastAPI，不读取应用全局状态，不创建第二份数据缓存。写入仍使用原子writer；不新增跨进程或跨文件事务。

## 旧实现与保留入口

已删除主程序内迁出的17项算法主体及仅为其服务的格式/规范化导入；没有保留第二套JSON读写/元数据更新/内容冲突算法。无生产调用的 main.canvas_path、main.load_canvas_any 包装已删除，路径测试改为检查隔离目录，路径规则本身由Store合同测试验证。

main.load_canvas、save_canvas、new_canvas、_write_canvas_document、_require_canvas_format、cleanup_expired_canvas_trash、iter_canvas_records、_project_canvases_for_move 仍由既有业务调用，只委托或转换错误。保留这些入口是为了不同时重写所有任务/助手/素材调用方；后续迁移对应应用服务时再逐项移除。

明确保留的不同职责：素材索引当前采用宽松JSON读取，与正式画布格式校验不同；媒体引用扫描、清空/日志删除的跨索引清理、备份恢复工具也不并入CanvasStore。本轮没有借模块化改变这些行为，不能宣称所有画布目录扫描都已统一。

## 实际界面与磁盘验收

仅使用公开代码副本、自制画布和独立端口：

1. 通过工作台新建中文普通画布，添加提示词并自动保存，重开后内容保留。
2. 通过真实创建/保存API准备智能画布，然后在真实页面编辑中文、刷新重开，内容保留。
3. 普通画布通过原生菜单重命名，移入回收站，勾选恢复，再打开，标题、项目归属及节点内容都保留。
4. 隔离磁盘核对两画布文字、已恢复状态、meta_revision与项目归属。

测试样例卡片最初坐标重叠造成误点，调整的是隔离数据的board坐标，未改产品布局或交互。普通画布新建/元数据/回收站使用原生界面；智能画布初始化由真实API完成，不把它描述为手动界面新建。
